Cryptography — Secrets, Proofs, and Post-Quantum Security

Cryptography is the mathematics of secure communication — ensuring confidentiality, integrity, authentication, and non-repudiation even in the presence of adversaries. It spans symmetric ciphers (AES), public-key systems (RSA, ECC), cryptographic hash functions, zero-knowledge proofs, multiparty computation, and post-quantum cryptography. The subject is built on computational hardness assumptions that separate feasible from infeasible.

"Anyone who considers arithmetical methods of producing random digits is, of course, in a state of sin."
— John von Neumann
Part 1

🔐 Symmetric-Key Cryptography and Shannon's Theory

Secrecy
Perfect Secrecy, Block Ciphers, and AES
Shannon's perfect secrecy: the ciphertext reveals no information about the plaintext — achieved by the one-time pad (OTP) with key length = message length, key uniform random, never reused. The OTP is unconditionally secure but impractical. Modern symmetric ciphers use product ciphers combining substitution and permutation. AES (Advanced Encryption Standard, Rijndael) is a 128/192/256-bit block cipher with 10/12/14 rounds of SubBytes, ShiftRows, MixColumns, AddRoundKey. The Feistel structure (DES, Blowfish, Twofish) splits the block into halves and alternates round functions. Modes of operation (CBC, CTR, GCM) extend block ciphers to encrypt arbitrary-length messages. Differential and linear cryptanalysis are the main attacks — AES was designed with proven bounds against these. Side-channel attacks exploit timing, power, or electromagnetic leakage rather than mathematical weaknesses.
Perfect secrecy requires keys as long as messages — all practical ciphers trade unconditional security for computational security based on assumptions.
Part 2

🔑 Public-Key Cryptography — RSA and Diffie-Hellman

Asymmetric
RSA, Diffie-Hellman, and the Discrete Logarithm Problem
Public-key cryptography (Diffie-Hellman, 1976) revolutionized security: each party has a public key (encryption) and private key (decryption). RSA (Rivest-Shamir-Adleman, 1977): choose primes p,q, n=pq, φ(n)=(p−1)(q−1), e coprime to φ(n), d = e^{-1} mod φ(n). Encrypt c = m^e mod n, decrypt m = c^d mod n. Security relies on the hardness of factoring n. The current factoring record: RSA-250 (829-bit, 2020). Diffie-Hellman key exchange: Alice sends g^a, Bob sends g^b, shared secret = g^{ab}. Security relies on the computational Diffie-Hellman (CDH) assumption. Elliptic curve cryptography (ECC) uses the group of points on an elliptic curve E: y² = x³ + ax + b over a finite field. ECC offers equivalent security to RSA with much shorter keys (256-bit ECC ≈ 3072-bit RSA). The ECDLP (elliptic curve discrete log) has no known subexponential attacks — the basis of ECC's efficiency.
Public-key cryptography solves the key distribution problem — security rests on number-theoretic problems like factoring and discrete log that are easy one way but hard to invert.
Part 3

🧾 Zero-Knowledge Proofs and Secure Computation

Proofs
Zero-Knowledge Proofs — Proving Knowledge Without Revealing It
A zero-knowledge proof (ZKP) allows a prover to convince a verifier of a statement's truth without revealing anything beyond the statement's validity. The classic example: proving you know a Hamiltonian cycle in a graph. ZKPs must satisfy completeness (honest prover convinces), soundness (cheating prover can't), and zero-knowledge (verifier learns nothing about the witness). Interactive proofs (Goldwasser-Micali-Rackoff, 1985) use multiple rounds. Non-interactive ZK (NIZK) via Fiat-Shamir heuristic uses a hash function. zk-SNARKs (Succinct Non-interactive ARguments of Knowledge) produce short proofs verifiable in milliseconds — used in Zcash and blockchain privacy. Secure multiparty computation (MPC) (Yao's garbled circuits, GMW protocol) allows n parties to compute a function on their private inputs without revealing them. The honest-majority setting (Shamir secret sharing, SPDZ) tolerates up to n/2 corrupted parties.
Zero-knowledge proofs enable a prover to convince a verifier of a fact without leaking any information — the ultimate privacy-preserving primitive.
Part 4

⚡ Post-Quantum Cryptography

Quantum Threat
Lattice-Based, Code-Based, and Multivariate Cryptography
Shor's algorithm (1994) factors integers and computes discrete logs in polynomial time on a quantum computer — breaking RSA, DSA, ECDSA, and Diffie-Hellman. Post-quantum cryptography designs schemes secure against quantum adversaries. The leading candidates: lattice-based (Learning With Errors — LWE, Ring-LWE). LWE: given (A, As+e) with small noise e, find s. Security reduces to worst-case lattice problems (GapSVP, SIVP). The NIST-selected winner CRYSTALS-Kyber (KEM) and CRYSTALS-Dilithium (signatures) are lattice-based. Also selected: FALCON (lattice signature) and SPHINCS+ (hash-based signature). Code-based cryptography (McEliece, Niederreiter) uses error-correcting codes — the Goppa code variant has survived decades of cryptanalysis but has large keys (256KB+). Multivariate cryptography (Rainbow, UOV) uses the hardness of solving systems of quadratic equations over finite fields. The NIST PQC standardization (2024) selected Kyber and Dilithium as primary algorithms, with Falcon and SPHINCS+ as alternatives.
Shor's algorithm kills RSA/ECC — post-quantum crypto (LWE, code-based, multivariate) is being standardized now to secure communications against future quantum computers.

Authenticated Encryption and AEAD Constructions

Authenticated Encryption with Associated Data (AEAD) combines confidentiality and integrity in a single primitive, eliminating the need for separate MAC‑then‑encrypt or encrypt‑then‑MAC compositions that are prone to implementation errors. The most widely deployed AEAD schemes are AES‑GCM (Galois/Counter Mode), standardized in NIST SP 800‑38D and RFC 5116, and ChaCha20‑Poly1305, specified in RFC 8439 for use in TLS 1.3 and QUIC. AES‑GCM uses a 96‑bit nonce and a 128‑bit authentication tag; its security proof reduces to the pseudorandomness of AES and the universality of the GHASH polynomial. ChaCha20‑Poly1305 replaces the block cipher with the ChaCha20 stream cipher and the polynomial MAC with Poly1305, offering comparable performance on platforms lacking AES‑NI. Both constructions require unique nonces per key — reuse leads to catastrophic loss of confidentiality and integrity, a property that has caused real‑world breaches in embedded devices.

Other notable AEAD modes include OCB (Offset Codebook), which achieves optimal block‑cipher calls but is encumbered by patents in some jurisdictions; CCM (Counter with CBC‑MAC), used in IEEE 802.11i and TLS 1.2, which processes data in two passes and imposes a maximum message length of 2⁶⁴−1 bytes; and EAX, a two‑pass mode built on OMAC that provides provable security under the PRP assumption. The CAESAR competition (2013‑2019) evaluated 57 candidates and selected Ascon, ACORN, and AEGIS as finalists for lightweight environments, highlighting the trade‑off between hardware footprint, side‑channel resistance, and software speed. Modern protocols such as TLS 1.3 mandate AEAD ciphersuites and forbid non‑AEAD constructions, reflecting a consensus that authenticated encryption is the baseline for any new deployment.

Implementation pitfalls remain a primary source of vulnerabilities. Nonce misuse resistance (e.g., AES‑GCM‑SIV, RFC 8452) mitigates accidental nonce reuse by deriving a per‑message synthetic IV from the plaintext and associated data, at the cost of an additional pass over the data. Developers must also ensure that the authentication tag is verified before any plaintext is released — a failure known as the “decryption oracle” leads to padding‑oracle‑style attacks even on AEAD. Constant‑time comparison of tags, proper handling of associated data lengths, and avoidance of branching on secret data are mandatory for side‑channel resilience.

Standardization bodies continue to refine AEAD guidance. NIST SP 800‑38D Rev. 1 (2023) adds recommendations for nonce generation using a monotonic counter or a cryptographically secure RNG, and clarifies the maximum number of encryptions per key (2³² for 96‑bit nonces). The IETF’s CFRG (Crypto Forum Research Group) maintains a registry of AEAD algorithms with assigned identifiers, enabling algorithm agility in protocols such as HPKE (Hybrid Public Key Encryption, RFC 9180). Understanding the exact security bounds — e.g., the 2⁻⁶⁴ forgery probability for AES‑GCM with a 128‑bit tag — is essential for risk assessments in high‑value systems.

In practice, the choice between AES‑GCM and ChaCha20‑Poly1305 often hinges on hardware acceleration. On x86‑64 with AES‑NI, AES‑GCM achieves sub‑cycle per byte throughput; on ARM Cortex‑M or RISC‑V cores without dedicated AES instructions, ChaCha20‑Poly1305 is typically faster and more energy‑efficient. Both are approved for protecting classified information up to TOP SECRET when used with 256‑bit keys and proper key management, per CNSA Suite 2.0.

Side‑Channel Countermeasures and Implementation Security

Side‑channel attacks exploit physical leakage — timing, power consumption, electromagnetic emanations, cache behavior, and even acoustic signals — to recover secret keys without breaking the underlying mathematics. The seminal timing attack on RSA (Kocher, 1996) demonstrated that variable‑time modular exponentiation leaks the exponent bits. Since then, differential power analysis (DPA) on smart cards (Kocher, Jaffe, Jun, 1999) and cache‑timing attacks on AES (Bernstein, 2005) have shown that software implementations on general‑purpose CPUs are equally vulnerable. The Spectre and Meltdown families (2018) further blurred the line between microarchitectural side channels and architectural bugs, forcing a reevaluation of constant‑time coding practices.

Countermeasures fall into three broad categories: algorithmic masking, hiding, and formal verification. Masking splits each sensitive variable into d shares (typically d = 2 or 3) such that any subset of d − 1 shares reveals no information; the ISW (Ishai‑Sahai‑Wagner) scheme provides provable security against d‑th‑order DPA under the probing model. Hiding aims to make the power trace independent of data, using techniques such as random clock jitter, dual‑rail precharge logic, or constant‑time instruction sequences. Formal verification tools like Jasmin, EasyCrypt, and the Cryptol language enable machine‑checked proofs that an implementation satisfies constant‑time and non‑interference properties.

For AES, the most common software defense is the use of bitsliced or vectorized implementations (e.g., the AES‑NI instruction set, ARMv8‑A Crypto Extensions) that execute the same instruction flow regardless of key or plaintext. When hardware acceleration is unavailable, table‑based implementations must be replaced by constant‑time S‑box computations (e.g., using the Boyar‑Peralta circuit) to avoid cache‑timing leakage. The OpenSSL and BoringSSL libraries have adopted “constant‑time” flags and rigorous testing via the ctgrind and dudect frameworks to detect data‑dependent branches and memory accesses.

Public‑key operations require additional care. RSA‑CRT (Chinese Remainder Theorem) decryption is vulnerable to fault attacks (Bellcore attack, 1997) and timing variations in the Montgomery multiplication loop. Countermeasures include exponent blinding (adding a random multiple of φ(n) to the private exponent), base blinding (multiplying the ciphertext by rᵉ mod n), and verification of the result by re‑encryption. ECC scalar multiplication must use a regular, constant‑time ladder (Montgomery ladder or Joye’s double‑and‑add‑always) and projective coordinates to avoid field inversions that leak via timing. The NIST SP 800‑56A Rev. 3 (2023) mandates side‑channel resistant implementations for all approved key‑agreement and signature schemes.

Physical countermeasures for embedded devices include on‑chip voltage and frequency regulators, noise generators, and active shields that detect probing attempts. The Common Criteria (ISO/IEC 15408) Evaluation Assurance Levels (EAL) 4+ and 5+ require evidence of side‑channel resistance, often demonstrated through Test Vector Leakage Assessment (TVLA) with millions of traces. In the post‑quantum era, lattice‑based schemes such as Kyber and Dilithium introduce new leakage surfaces — polynomial multiplication via NTT (Number Theoretic Transform) and sampling from discrete Gaussians — that must be hardened with the same rigor as classical primitives.

Worked Example: Constant‑Time AES‑128 S‑Box
Show how to compute the AES S‑Box output for a given input byte using only bitwise operations and fixed‑depth arithmetic, ensuring no data‑dependent branches or memory accesses. Provide the sequence of operations and explain why this construction is constant‑time.
The AES S‑Box is the composition of a multiplicative inverse in GF(2⁸) (with 0 mapping to 0) followed by an affine transformation. A constant‑time implementation computes the inverse using the Itoh‑Tsujii algorithm: for an 8‑bit element x, compute x⁻¹ = x²⁵⁴ = x²·x⁴·x¹⁶·x³²·x⁶⁴·x¹²⁸ (exponents are powers of two). Each squaring in GF(2⁸) is a linear operation (bit‑permutation) and each multiplication is a fixed sequence of shifts and XORs with the reduction polynomial 0x11b. The affine transform is a fixed 8×8 binary matrix multiplication plus a constant vector, again realized with bitwise AND, XOR, and rotations. Because the control flow does not depend on the value of x — every step executes unconditionally — the routine runs in exactly the same number of cycles for any input, eliminating timing and cache side channels.
Exam‑Day Strategy
When a question asks for a side‑channel resistant design, first identify the primitive (block cipher, RSA, ECC, lattice). Then list the relevant leakage sources (cache, timing, power, fault) and map each to a standard countermeasure (bitslicing, masking, blinding, constant‑time ladder). Cite the applicable standard (e.g., NIST SP 800‑56A Rev. 3 for ECC, FIPS 140‑3 for module validation). This structured answer scores higher than a generic “use constant‑time code”.

Key Derivation Functions and Password Hashing

Key Derivation Functions (KDFs) transform high‑entropy secrets (Diffie‑Hellman shared secrets, master keys) or low‑entropy passwords into uniformly distributed cryptographic keys. The distinction between entropy‑extracting KDFs (HKDF, RFC 5869) and password‑hashing KDFs (PBKDF2, bcrypt, scrypt, Argon2) is critical: the former assume the input already has sufficient min‑entropy and focus on domain separation and key expansion; the latter deliberately introduce computational and memory hardness to slow down offline guessing attacks.

HKDF‑Extract uses HMAC‑Hash (typically HMAC‑SHA‑256) with a salt to produce a pseudorandom key (PRK); HKDF‑Expand then derives arbitrary‑length output keying material (OKM) using a counter‑based construction. This two‑step design enables key separation for multiple protocols (e.g., TLS 1.3 derives traffic keys, IVs, and resumption secrets from a single HKDF‑Expand call with distinct info strings). The security proof reduces to the PRF security of HMAC and the random‑oracle model for the hash function.

PBKDF2 (RFC 8018) applies HMAC‑Hash iteratively c times (typically c ≥ 100 000) to the password and salt. Its sequential nature limits parallelism but offers no memory hardness, making it vulnerable to GPU/ASIC acceleration. bcrypt (1999) incorporates a Blowfish‑based key schedule with a configurable cost factor (log₂ iterations) and a 128‑bit salt; its memory footprint (~4 KB) provides modest resistance to custom hardware. scrypt (2009) introduces a memory‑hard function parameterized by N (CPU/memory cost), r (block size), and p (parallelization), requiring N·r·128 bytes of RAM; typical parameters (N=2¹⁴, r=8, p=1) demand ~16 MiB, raising the cost of large‑scale cracking.

Argon2, the winner of the Password Hashing Competition (2015), comes in three variants: Argon2d (data‑dependent memory access, maximal GPU resistance), Argon2i (data‑independent, preferred for side‑channel resistance), and Argon2id (hybrid, recommended for general use). Argon2id with parameters t=3 passes, m=64 MiB, p=4 lanes is the current baseline for interactive logins per OWASP and NIST SP 800‑63B. The algorithm’s design includes a Blake2b‑based compression function and a memory‑filling phase that is provably memory‑hard under the parallel random‑oracle model.

Implementation guidelines: always use a unique, cryptographically random salt per password (minimum 128 bits); store the salt, algorithm identifier, and parameters alongside the hash (e.g., in the modular crypt format `argon2idv=19$m=65536,t=3,p=4$...`); enforce a maximum password length (e.g., 72 bytes for bcrypt, 4 GiB for Argon2) to avoid denial‑of‑service via excessive hashing time; and periodically re‑hash with upgraded parameters during successful authentication. For key derivation from high‑entropy sources, prefer HKDF‑SHA‑256 or HKDF‑SHA‑384 with a fixed‑length salt (e.g., 32 bytes) and distinct info strings per key purpose.

Threshold Cryptography and Distributed Key Generation

Threshold cryptography splits a secret key among n parties such that any subset of size t (≤ n) can jointly perform a cryptographic operation (signing, decryption) while smaller subsets learn nothing. The foundational primitive is Shamir’s Secret Sharing (1979): a dealer samples a random polynomial f(x) of degree t‑1 over a finite field, sets the secret s = f(0), and distributes shares f(i) to party i. Reconstruction uses Lagrange interpolation; any t shares uniquely determine f(0). This information‑theoretic scheme underpins many threshold protocols.

Distributed Key Generation (DKG) removes the trusted dealer. The Pedersen DKG (1991) lets each party act as a dealer for a Shamir sharing of its own random value, then combines the shares to form a joint public key gˣ where x is the sum of the secret contributions. Verifiable Secret Sharing (VSS) — using Feldman commitments (gf(i)) or Pedersen commitments (gf(i)hr(i)) — ensures that malicious parties cannot distribute inconsistent shares. The Gennaro‑Jarecki‑Krawczyk‑Rabin (GJKR) DKG (1999) achieves robustness against up to t‑1 corrupt parties in the synchronous model and is the basis for modern threshold BLS signatures and threshold ECDSA (e.g., the GG18 and GG20 protocols).

Threshold signatures enable a group to produce a single compact signature verifiable under a single public key. BLS signatures (Boneh‑Lynn‑Shacham, 2001) are particularly amenable: each party computes a partial signature σᵢ = H(m)xᵢ on the same message, and the combiner aggregates them using Lagrange coefficients to obtain σ = ∏σᵢλᵢ = H(m)∑xᵢ = H(m)x. The aggregation is non‑interactive and the resulting signature is indistinguishable from a standard BLS signature. Threshold ECDSA is more involved because the nonce k must also be shared; protocols such as Lindell‑Nof (2017) and the later CGGMP (2020) achieve two‑round signing with identifiable abort, and are deployed in custody solutions for cryptocurrency wallets.

Applications extend beyond blockchain. Threshold decryption is used in secure voting (e.g., Helios, Belenios) where the election private key is shared among trustees; any t trustees can decrypt the tally but fewer cannot. In hardware security modules (HSMs), threshold ECDSA allows multi‑party authorization for high‑value transactions without a single point of compromise. The NIST SP 800‑56C Rev. 2 (2020) includes guidance on threshold key agreement, and the IETF’s CFRG is standardizing a Threshold Signature Scheme (TSS) based on FROST (Flexible Round‑Optimized Schnorr Threshold) for use in MLS (Messaging Layer Security) and other group messaging protocols.

Security considerations: the threshold t must be chosen to balance availability and confidentiality; a common rule is t = ⌊n/2⌋ + 1 for honest‑majority settings, while proactive secret sharing (Herzberg‑Jarecki‑Krawczyk‑Yung, 1995) periodically refreshes shares to tolerate mobile adversaries. Side‑channel resistance of the share‑generation and signing code is essential — each party’s partial computation must be constant‑time. Finally, the communication model (synchronous vs. asynchronous) dictates the achievable robustness; asynchronous DKG (e.g., Kate‑Zaverucha‑Goldberg, 2010) tolerates network delays but requires stronger cryptographic assumptions (pairing‑based).

Homomorphic Encryption and Secure Computation

Homomorphic Encryption (HE) allows computation on ciphertexts without ever decrypting, producing an encrypted result that decrypts to the same value as if the operation had been performed on plaintexts. The first fully homomorphic scheme (Gentry, 2009) used ideal lattices and bootstrapping — a procedure that refreshes ciphertext noise by evaluating the decryption circuit homomorphically. Subsequent generations improved efficiency: the BGV (Brakerski‑Gentry‑Vaikuntanathan, 2012) and BFV (Fan‑Vercauteren, 2012) schemes operate over the ring R_q = ℤ_q[x]/(xⁿ+1) with modulus switching; CKKS (Cheon‑Kim‑Kim‑Song, 2017) supports approximate arithmetic on real numbers, enabling privacy‑preserving machine learning.

Performance is characterized by three parameters: the ring dimension n (typically 2¹⁴–2¹⁵), the ciphertext modulus q (product of several 30‑60‑bit primes), and the noise budget. A fresh ciphertext has noise ≈ √n; each homomorphic multiplication squares the noise, while addition adds it. Bootstrapping reduces noise to a fresh level but costs several seconds for n=2¹⁴ on a single core. Modern implementations (Microsoft SEAL, PALISADE, OpenFHE, TFHE‑2) use the Number Theoretic Transform (NTT) for polynomial multiplication, achieving ~10⁴ multiplications per second for BFV with 128‑bit security.

Applications include private information retrieval (PIR), encrypted database queries, and secure outsourcing of linear regression. For example, a hospital can send encrypted patient records to a cloud provider that computes a logistic regression model on the ciphertexts using CKKS, returning an encrypted model that only the hospital can decrypt. The noise growth in CKKS is managed by rescaling (dividing by a factor Δ) after each multiplication, which introduces a small approximation error but keeps the noise bounded.

Secure Multiparty Computation (MPC) complements HE: while HE is non‑interactive but heavy, MPC (e.g., GMW, SPDZ, ABY) distributes the computation among parties with lightweight secret‑shared arithmetic. Hybrid protocols (e.g., HE‑MPC switching) use HE for the input‑encoding phase and MPC for the bulk of the computation, achieving orders‑of‑magnitude speedups. The MP‑SPDZ framework implements such hybrids and supports both Boolean and arithmetic circuits.

Standardization efforts are underway. The HomomorphicEncryption.org community publishes security and API standards (HE Standard v1.1, 2021) defining parameter sets for 128‑bit security across BFV, BGV, CKKS, and TFHE. NIST has initiated a lightweight cryptography project that includes HE‑friendly primitives, and the ISO/IEC JTC 1/SC 27 working group is drafting a standard for homomorphic encryption interfaces. Understanding the trade‑off between ciphertext size (typically 1–2 MiB per ciphertext for BFV with n=2¹⁴), latency, and the depth of the supported circuit is essential for system architects evaluating privacy‑preserving analytics.

  • Assuming AEAD nonce reuse is harmless — it destroys both confidentiality and integrity.
  • Using PBKDF2 with a low iteration count (e.g., c=1000) for password storage — modern GPUs can test billions of candidates per second.
  • Believing that constant‑time code alone defeats all side channels — microarchitectural effects (Spectre, cache‑line sharing) require additional mitigations.
  • Treating threshold signatures as a drop‑in replacement for single‑party signatures without verifying the DKG robustness model.
  • Choosing HE parameters solely on ciphertext size without accounting for noise growth and bootstrapping cost.
  • Ignoring the need for domain separation in HKDF — using the same PRK for unrelated keys leads to cross‑protocol attacks.
  • Assuming that a single VSS round guarantees security against a rushing adversary in asynchronous networks.

These advanced topics form the core of modern cryptographic engineering and are essential for designing systems that remain secure against both classical and emerging threats.
